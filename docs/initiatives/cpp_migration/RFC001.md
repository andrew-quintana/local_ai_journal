# RFC001 — llama.cpp Migration Technical Architecture

## Design Overview

This RFC defines the technical architecture for migrating from Ollama to llama.cpp while maintaining API compatibility and adding comprehensive cross-platform support including Windows native builds. The system provides direct hardware acceleration through Metal, CUDA, and DirectML while preserving existing workflows.

### Architecture Principles
1. **Performance First**: Direct hardware access without abstraction overhead
2. **Cross-Platform Parity**: Consistent behavior across macOS, Linux, and Windows
3. **API Compatibility**: Preserve existing OpenAI-compatible endpoints
4. **Docker Baseline**: Portable CPU inference for testing and development
5. **Graceful Fallback**: Runtime selection with rollback capability

   ```python
   # Core benchmark functions
   def benchmark_latency(endpoint, prompts):
       """Measure TTFT and token generation speed"""
       results = []
       for prompt in prompts:
           start_time = time.time()
           response = call_api(endpoint, prompt)
           ttft = response.first_token_time - start_time
           total_time = time.time() - start_time
           tokens = len(response.tokens)
           results.append({
               'ttft': ttft,
               'tokens_per_second': tokens / total_time,
               'total_latency': total_time
           })
       return results
   ```

4. **Hardware Detection and Optimization**
   ```bash
   # Automatic hardware detection
   detect_and_optimize() {
       local platform=$(uname -s)
       local hardware=""
       
       case $platform in
           "Darwin")
               if system_profiler SPDisplaysDataType | grep -q "Metal"; then
                   hardware="metal"
               else
                   hardware="cpu"
               fi
               ;;
           "Linux")
               if which nvidia-smi >/dev/null 2>&1; then
                   hardware="cuda"
               else
                   hardware="cpu"
               fi
               ;;
           "MINGW"*|"MSYS"*)
               if where nvidia-smi >nul 2>&1; then
                   hardware="cuda"
               else
                   hardware="directml"
               fi
               ;;
       esac
       
       optimize_for_hardware $hardware
   }
   ```

## Security Considerations

### Threat Model
- **Assets**: Model files, API endpoints, performance data, runtime configurations
- **Threats**: Unauthorized access, model tampering, performance degradation, API abuse
- **Mitigations**: Localhost binding, file integrity validation, access control, monitoring

### Security Controls
1. **Network Security**
   - All servers bound to localhost (127.0.0.1) only
   - No external network access for inference operations
   - Container network isolation maintained
   - API endpoint access control preserved

2. **Model Security**
   - GGUF model checksum validation before loading
   - Model files stored within encrypted vault boundary
   - Access control for model directory
   - Secure model conversion pipeline

3. **Runtime Security**
   - Process isolation and privilege restrictions
   - Resource limits to prevent DoS
   - Secure credential handling for runtime selection
   - Monitoring for unusual behavior patterns

## Migration and Rollout Strategy

### Gradual Migration Approach
1. **Phase Rollout**
   - Docker baseline first for compatibility validation
   - Single platform native optimization (macOS)
   - Additional platform support (Linux, Windows)
   - Full production deployment with monitoring

2. **A/B Testing Framework**
   - Side-by-side runtime comparison
   - Performance metrics collection and analysis
   - Quality validation through automated testing
   - User acceptance criteria validation

3. **Rollback Procedures**
   - Environment flag for instant runtime switching
   - Automated health monitoring with failover
   - Complete system state preservation
   - Recovery procedures for each failure mode
